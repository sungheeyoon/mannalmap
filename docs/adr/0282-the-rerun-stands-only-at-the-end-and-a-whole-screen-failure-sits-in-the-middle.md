# 풀이 끝의 「다시 받기」는 수정 전 글에도 글 끝에만 서고, 화면 통째 실패는 가운데에 선다

> **운영자 결정 2026-11-27(낮, 앱 점검 열 건의 전후 그림을 보고).** 「A3 … 이거 다 좋은데 다시받기 버튼이 맨 위에 있는 건 별로여서 맨 아래 뒀었어.
> 맨 아래 있으니 지워도 될 듯」 · 「실패꼴은 처음 그림인 가운데 정렬이 더 좋지 않냐?」
>
> 이 결정이 대체하는 것 — ADR 0133 (일부: 덧의 「수정 전 글이면 다시 받기는 머리의 주 단추로 남는다」) · ADR 0281 (일부: 「화면 통째 실패는 실패 줄 하나」의
> 자리 — 글자 · 단추는 그대로, 자리만 가운데)

## 정한 것

1. **글이 있을 때 「다시 받기」는 수정 전 정보로 만든 글이어도 글 끝에만 선다** — 보내기와 반반(보내기가 없으면 혼자 주 단추). 머리의 주 단추를 걷는다.
   수정 전이라는 사실은 결과 화면 머리의 안내 줄(`READING_STALE_NOTE`)이 말한다. 웹(`app/me/reading/panel.tsx`) · 앱(`mobile/src/reading/panel.tsx`) 같다.
2. **화면 통째 실패는 화면 가운데에 선다** — 그 화면에 실패 말고 설 것이 없을 때(앱 관문의 껍데기 · 풀이 보관함 · 풀이 · 소식). 실패 줄(`FailureLine`)의
   글자와 단추는 그대로이고 자리만 가운데다. 화면 한쪽의 부분 실패(누름 실패 · 칸 하나의 실패)는 제자리 그대로다.

## 까닭

1. 「안 A」(2026-10-26)가 다 읽은 뒤에 하는 일을 글 끝에 모았는데, 수정 전 글만 예외로 머리에 주 단추가 남아 있었다(시안 3차 warm 의 「읽기 전에 정한다」).
   운영자는 위의 단추를 원래 아래로 내린 것으로 보고 있었고, 같은 일에 손잡이는 하나라 끝에 있으면 위는 필요 없다고 정했다.
2. 화면 전체가 실패만 말할 때는 빈 화면 · 기다림 같은 다른 「화면 전체의 상태」처럼 가운데에 서는 쪽이 낫다고 운영자가 골랐다(점검 전후 그림에서 고친 뒤의
   왼쪽 정렬과 고치기 전의 가운데를 나란히 보고). 꼴(붉은 한 줄 + 다시 시도)은 ADR 0281 그대로 한 벌이다.
