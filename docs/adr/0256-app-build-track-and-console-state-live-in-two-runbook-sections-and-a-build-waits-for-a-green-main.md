# 앱 빌드 · 트랙 · Play 콘솔 차례의 지금 상태는 런북 두 절에만 적고, 앱은 묶어서 main 의 검증이 통과한 커밋에서 굽는다

> **운영자 답 2026-11-19 「다 시작」**(조율자가 옮김) — 그날 감사가 찾은 것을 모두 고친다 · 문서 고침은 자동 머지. 이 ADR 은 그 감사의 둘 —
> 원본이 없는 앱 · 콘솔 사실과 굽는 차례의 빈칸 — 을 정한다. 결정 점검표의 「검증 · 배포의 문턱」(아래 「정한 것」 5 의 셋째 — 앱 빌드가
> main 의 검증을 기다린다)에 걸린다. ADR 0240 「정한 것」 3 의 원본 표 넷은 그대로이고, 이 ADR 은 그 표가 덮지 않는 사실의 자리를 더한다.

## 확인한 것 (2026-11-19, `1da9819e`)

**사실 하나가 다섯 자리에 따로 적혀 서로 갈렸다.** ADR 0240 의 원본 표(2026-11-08)는 웹 Production SHA · 운영 DB 의 마이그레이션 ·
권한 날짜 · 출시 단계 넷이다. 그날은 Play 계정도 AAB 도 없었다 — 개인 개발자 계정은 2026-11-10, 첫 AAB 는 2026-11-11 이다(ADR 0246).
그 뒤 아흐레 동안 Play 에 올린 버전이 다섯(versionCode 2 · 3 · 5 · 6 · 10)이고 굽기만 하거나 실패한 번호가 넷(4 · 7 · 8 · 9)이며,
콘솔의 차례(계정 · 앱 · 키 · 상품 · 등록정보 · 테스터)가 거의 날마다 움직였다. 그 값을 적은 자리가 따로 놀았다.

- `docs/ops/runbook/mobile-release.md` 안에서 — EAS 환경값 표(122줄)는 「`production` · iOS 빌드는 아직 없다」, 빌드 줄(166줄)은 `production`
  10 · 6 · 5 … 를 적었고, 그 줄 끝의 「내부 테스트 트랙에는 versionCode 2 가 남아 있다」는 같은 줄 첫머리(내부 테스트에 10 을 올렸다)와 어긋났다
- `docs/ops/runbook/play-console.md` 상태 표 — 차례 8 의 「테스터 목록은 아직 없다」와 같은 표 「내부 테스트로 깔아 보기」의 목록 `operator`
- `docs/ops/runbook/kakao-login.md` 7 · 36줄의 「앱은 실기기 확인 전」 · 「`production` 빌드는 아직」과 `play-console.md` 차례 9 의
  「Play 내부 테스트로 깐 앱에서 구글 · 카카오 로그인이 됐다(2026-11-11)」
- 간극 대장 — G-123 · G-131 「지금 판 `477348f4`」, G-128 「상품 넷이 아직 없다」(2026-11-17 에 만들었다), G-162 「테스터를 아직 모으지
  않았다」(2026-11-11 그룹 17명), G-21 「배포 … 남음」(2026-11-17 배포). G-164 는 끝 조건 셋이 2026-11-17 에 다 찼는데 열려 있었다
- #770 머리의 「앱 Play 비공개 테스트 `6 (1.0.0)`」(맞는 값이지만 다섯째 자리다)와 D 첫 문단의 「#1142 · #1155 … 다음 AAB 가 싣는다」(둘 다
  versionCode 10 의 커밋에 있다)

**까닭 — PR 없이 하는 일에는 문서를 고치는 걸음이 없었다.** 웹 배포는 「묶음 배포」 5 가 #770 에 댓글을 적게 하지만, 콘솔 · Play 의 일(상품을
만들고 · 키를 넣고 · 버전을 올리고 · 테스터를 받는 것)에는 끝난 뒤 대장 · 런북을 고치는 걸음이 차례표에 없었다. 운영자는 같은 일을 「코드랑
문서랑 정책 따로놀아」(2026-11-06) · 「배포 하기 전에 지금 한 거 문서로 안 정리하지 않았냐?」(2026-11-17)로 여러 번 짚었다.

**굽는 차례의 빈칸 셋.**

- 2026-11-19 EAS Free 의 이달 Android 빌드 횟수를 다 써서 클라우드 빌드가 멈췄다(다음 달 1일에 풀린다). 남은 수를 미리 본 적이 없었고, PC 로컬
  빌드로 옮겨 굽다가 WSL 의 `/tmp` 가 차고 재부팅까지 갔다(`mobile-release.md` 「무료 빌드 횟수가 떨어지면」의 함정 셋). 운영자: 「한달 제한이
  있으니 보고하고 했으면 좋겠다, 경고를」
- 2026-11-12 비공개 테스트 중에 versionCode 3 → 4 → 5 로 나눠 구웠고 4 는 굽고 버렸다. 운영자: 「그런데 왜 한 번에 처리 안 하고 한 번씩 하는
  거야」. 「묶는다」는 그 뒤 빌드 줄의 덧말에만 있었고 차례의 걸음이 아니었다
- versionCode 10 은 커밋 `c61303aa` 로 구웠는데, 그 커밋의 2026-11-19 일정 `verify` 는 `audit` · `mobile` 차선이 실패였다(머지 때의 push 실행은
  성공). 굽는 커밋의 검증을 보는 걸음이 앱 런북에 없다 — 웹은 「묶음 배포」 0 이 main CI 를 본다(ADR 0159)

## 정한 것

1. **앱 빌드의 지금 상태는 `docs/ops/runbook/mobile-release.md` 「지금 나간 빌드」 하나가 원본이다** — 트랙마다 지금 버전(Play 내부 테스트 ·
   비공개 테스트 · 프로덕션, EAS 내부 배포, iOS)과 빌드 목록(빌드 · 커밋 · versionCode · 날짜 · 올린 곳 · 포함된 PR). 빌드를 굽거나 트랙에
   올린 날 그 절을 고친다.
2. **Play 콘솔 차례의 지금 상태는 `docs/ops/runbook/play-console.md` 「지금 어디까지 왔나」 하나가 원본이다** — 「계정을 만드는 날의 차례」
   1 ~ 14 마다 한 줄과, 차례 밖의 콘솔 일(15% 서비스 수수료 · 내부 테스트의 테스터 목록 · 비공개 테스트의 14일 · `eas submit` 의 403).
   버전은 적지 않고 1 을 가리킨다.
3. **다른 자리는 값을 다시 적지 않고 가리킨다** — 간극 대장의 G 줄 · `kakao-login.md` 같은 다른 런북 · #770 머리. G 줄은 「`play-console.md`
   「지금 어디까지 왔나」 13」처럼 차례 번호로 가리킨다. 그날 무엇을 했나는 G 기록 파일 · #770 댓글에 남는다 — 그날의 기록이라 낡아도 된다
   (ADR 0090 「잠그지 않은 것」과 같은 결).
4. **차례가 끝나면 그 차례를 가리키는 G 줄을 같은 PR 에서 고친다** — 콘솔 일이면 1 · 2 를 고치는 문서 PR 에서, 웹 배포면 「묶음 배포」 5 의
   댓글 뒤 문서 PR 에서. 끝 조건이 찼으면 줄을 닫고 changelog 에 적는다(대장 머리말).
5. **굽기 전에 셋을 본다**(`mobile-release.md` 「빌드와 제출」 앞머리)
   - EAS 의 이달 남은 Android 빌드 수를 운영자에게 한 줄로 알리고, 다 써 가면 경고한다 — 실패 · 중단한 빌드도 한 번으로 센다
   - 앱 손질은 묶어서 한 번에 굽는다 — 화면 PR 이 승인될 때마다 굽지 않는다. 테스터 누구나 겪는 결함 하나만 먼저 낼 수 있다
   - 굽는 커밋은 main 의 `verify` 의 가장 최근 실행이 성공인 커밋이다 — 웹 「묶음 배포」 0 과 같은 기준이다

## 견준 것

- **G 줄 칸에 지금 값을 적고 바뀔 때마다 함께 고친다** — 지금까지의 방식이고, 아흐레에 여섯 줄이 낡았다.
- **#770 머리를 원본으로** — 이슈 본문은 저장소 시험이 못 읽고, 운영자의 체크 목록이라 끝난 줄과 지금 값이 섞인다. #770 은 웹 배포 댓글의
  자리(ADR 0240)로만 둔다.
- **런북 한 절에 빌드와 콘솔을 함께** — 콘솔 차례의 번호와 걸음은 `play-console.md` 「계정을 만드는 날의 차례」에 있어, 상태를 같은 파일에 두면
  차례와 상태가 나란하다. 빌드는 iOS · EAS 내부 배포까지 걸쳐 Play 의 파일에 두지 않는다.
- **앱도 `scripts/deploy-range.mjs` 로 가린다** — 그 스크립트는 웹 Production 과 main 사이의 범위를 본다. 앱은 굽는 커밋 하나의 실행 결과만 보면
  되어 `gh run list` 한 줄로 둔다.

## 받아들인 것

- 두 절을 고치는 것은 사람 · 에이전트의 걸음이다 — 시험은 콘솔의 실제 상태를 모르고, 두 절과 G 줄이 서로 맞는지도 견주지 않는다.
- 빌드 목록은 길어진다 — 프로덕션 출시 뒤 지난 빌드를 다른 곳으로 옮길지는 그때 정한다.
