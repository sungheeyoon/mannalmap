# 정지된 계정도 제 프로필 사진 · 소개를 지울 수 있다 — 제 사진을 보고 한 장씩 지우기만 열고, 올리기 · 고치기는 그대로 막는다

> **운영자 지시 2026-11-08**(조율자가 옮김, G-153 의 일부) — 「처리방침에 『프로필 화면에서 삭제할 수 있습니다』를 예외 없이 쓰려면 정지 계정도
> **지우기만** 되어야 한다. 허용은 사진 삭제와 소개 비우기뿐, 수정 · 올리기 · 순서 바꾸기 · 닉네임 변경은 계속 막는다. 소개 삭제는
> `save_my_profile` 을 넓히지 말고 전용 문을 먼저 검토한다」. 결정 점검표의 「누가 무엇을 할 수 있는가」(정지된 사람이 부르는 문의 경계)에 걸린다.
> **운영자 답 2026-11-08 「(나)」**(조율자가 옮김) — 사진 일부 삭제는 정지된 사람에게도 **제 사진만 보이게 열고 한 장씩 지우게** 한다. 고객센터 문의 줄과
> 수동 절차는 두지 않는다 — 「모두 지우기만 두고 골라 지우려면 문의」(안 가)는 운영자가 손으로 지우는 절차를 남긴다.
> 2026-09-30(#384)에 정지된 사람의 「사진 전부 내리기」(`clear_my_photo`)를 닫은 것을 지우기 한 갈래만 되연다.

## 잰 것 (2026-11-08, main `8944d4cd`)

- `remove_my_photo` 는 `lock_my_photos()` 를 거치고, 그 함수가 `is_active_account()` 로 정지 · 탈퇴 대기를 「이용이 정지된 계정입니다.」(`42501`)로
  거절한다(`20270104090000`). 소개를 비우는 길은 `save_my_profile(닉네임, 소개)` 하나이고 그 문도 같은 문장으로 거절한다.
- **웹 · 앱 둘 다 정지된 사람에게 프로필 화면을 통째로 안 세운다** — 웹 `/me/profile` 은 `isBlocked(state)` 면 안내 상자 하나만
  (`app/me/profile/page.tsx`), 앱의 프로필 화면도 같다(`mobile/src/settings/profile-screen.tsx`). 설정의 「내 프로필」 줄도 이용 중일 때만 선다.
- 정지된 사람은 제 사진을 **볼 수 없다** — 사진 주소의 판정(`may_see_photo`)이 `is_active_account()` 를 먼저 묻는다. 제 사진의 자리 · 판본
  (`my_photos`)과 제 계정 행(소개)은 읽힌다.
- 운영 DB(2026-11-08, 개수만): 인연 참여를 켠 사람 2 · 그 가운데 사진 1 · 소개 1, 둘 다 운영자 계정. 이용 중이 아닌 계정 0. `match_open` 은 닫힘.

## 정한 것

1. **`remove_my_photo` 는 계정 상태를 묻지 않는다** — 로그인만 묻는다. `lock_my_photos()` 와 같은 계정 행을 `for update` 로 잠가 같은 사람의
   올리기 · 옮기기와 차례로 선다. 본문은 그대로다(판본이 다르면 조용히 지나간다 · 뒤의 장이 당겨 앉는다). 저장소 객체는 표의 트리거
   (`profile_photo_object_left`)가 지울 줄에 넣으므로 상태와 무관하게 돈다.
2. **소개는 전용 문 `clear_my_intro()` 로 비운다** — 인자가 없고 `intro` 를 `null` 로만 둔다. `save_my_profile` 은 넓히지 않는다 — 닉네임이
   함께 실리는 문이라 넓히면 「소개를 비우며 닉네임을 바꾸기」가 열린다. 권한은 `authenticated` 만(`anon` · `public` 은 닫는다).
3. **올리기 · 바꾸기 · 옮기기 · 보일 자리 · 닉네임 · 소개 쓰기는 그대로 막힌다** — `lock_my_photos()` · `save_my_profile` 은 안 건드린다.
4. **자기 사진은 계정 상태와 상관없이 본인에게 보인다** — 바이트를 내는 문 `photo_at` 이 본인이면 판정(`may_see_photo`)을 묻지 않는다. 남에게 보이는가는
   `may_see_photo` 그대로다 — 정지된 사람의 사진은 남에게 계속 안 보이고(상대의 `status = 'active'` 를 묻는다), 정지된 사람도 남의 사진을 못 본다.
   웹의 지우는 판은 사진을 보이고 장마다 「삭제」를 둔다(사진 칸의 삭제 확인 그대로, ADR 0205).
5. **DB 는 정지와 탈퇴 대기를 가르지 않는다** — 둘 다 지우기만 된다. 탈퇴 대기는 3일 안에 어차피 지워지고, 지우기는 남에게 해가 없다.
   화면의 길은 정지된 사람에게만 연다(탈퇴 대기는 이미 처분을 기다린다).
6. **차례 — 넓히기다.** 새 문 하나와 거절을 하나 덜 하는 문 둘(`remove_my_photo` · `photo_at`)이라 옛 앱 · 옛 웹에 안전하다. 마이그레이션이 든 PR 은 `db push` 와 확인이 끝난 뒤
   머지한다(`docs/agents/delegation/permissions.md` 「예외 — 마이그레이션이 든 PR」): 운영자 검토 → `db push`(dry-run 먼저) · `migration list` 확인 →
   마이그레이션 PR 머지 → 화면 PR 머지 → 「배포」 답 뒤 웹 배포.

## 버린 것

- **`save_my_profile` 을 정지에 열고 닉네임이 그대로일 때만 받기** — 한 문이 상태에 따라 받는 인자의 뜻이 달라진다. 「소개를 고쳐 쓰기」를
  막으려면 또 갈래가 든다. 지우기만 하는 문이 경계를 이름으로 든다.
- **사진 지우기 전용 문을 새로 두기** — `remove_my_photo` 의 서명 · 앱의 부름이 그대로 쓰인다. 문을 늘리면 앱 PR 이 따라 든다.
- **(가) 사진은 모두만 지우고, 골라 지우려면 고객 문의** — 처음 PR 의 모양이었다. 운영자가 손으로 지우는 절차가 남아 (나)로 바꿨다(2026-11-08).
- **`may_see_photo` 자체를 본인에게 열기** — 그 판정의 본문(후보 · 지나친 사람 · 요청)을 다시 옮겨 적어야 하고, 판정을 부르는 자리가 `photo_at`
  하나라 바이트 문에서 본인을 먼저 가르는 것과 같은 결과다.

## 이 결정이 아닌 것 (운영자 답 2026-11-08, 조율자가 옮김)

- **사진과 소개는 따로 지운다** — 문이 둘이고(`remove_my_photo` · `clear_my_intro`) 화면의 단추도 따로다(사진은 장마다, 「소개 삭제」).
- **「삭제한 … 되돌릴 수 없어요」는 참이다** — 지운 줄은 DB 에서 바로 빠진다. 저장소 객체는 지울 줄(`photo_object_trash`)에 들어가는데 그 표를 읽는 것은
  청소기(`app/api/cron/photo-sweep/sweep.ts` → `DeleteObjects`)뿐이고 되살리는 문은 없다. 버킷의 버전 관리는 꺼 둔다(`docs/ops/runbook/photo-store.md`).
- **앱은 지우는 화면을 따로 짓지 않는다** — 앱 설정의 「프로필 사진 · 소개 삭제」 줄이 업데이트 화면과 같은 웹 계정 관리(`/me/settings`)를 앱 안 브라우저로 연다.
