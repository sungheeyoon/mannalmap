# 인연의 성인 확인은 꺼진 스위치 뒤에 먼저 세우고, 켜는 것은 후속 배포와 함께 승인받는다

> **운영자 결정 2026-11-02**(이슈 #947 댓글 · 조율자가 옮김) — 「운영 DB 에 성인 확인 차단을 먼저 적용해 지금 배포된 웹 · 앱의 인연을 막지 않는다. 이번에 드는 것은 호환 가능한 준비까지: 기본값이 꺼진 스위치 · 옛 앱에 영향 없는 표와 함수 · 앱의 안내와 복귀 동선 · 시험. 활성화(스위치 켜기)와 그 차단이 든 앱은 후속 배포와 함께 승인받는다.」 인연 시작 때 최초 1회라는 자리도 운영자 답이다(2026-11-02, #947 본문).
>
> 결정 점검표의 「누가 무엇을 할 수 있는가」 · 「실패했을 때 열리는가 닫히는가」 · 「데이터의 보존」에 걸린다. **꺼진 동안은 어느 답도 안 바뀐다** — 판정은 켜는 날 다시 묻는다.

## 잰 것 (2026-11-02, main `d82254ad`)

- 인연을 보이는 문은 열네 자리다. 표를 바로 읽는 길은 `chat_message` · `chat_room` 의 정책이 `chat_room_readable` 을 거쳐 하나로 모인다.
- 켜면 웹의 `my_discovery_board` 거절이 오류 경계로 간다(`app/me/matching/page.tsx`). 웹에는 아직 안내가 없다 — 이번 범위가 아니라 활성화의 조건이다.
- 켜면 옛 앱은 인연 탭에 거절 문장과 「다시 시도하기」만 보인다. 확인할 길이 없다 — 그래서 켜기가 앱 배포 뒤다.

## 정한 것

1. **스위치** `adult_check_switch` 는 한 줄이고 기본값은 꺼짐이다. 어느 마이그레이션도 켜지 않는다. 켜는 것은 `docs/ops/runbook/adult-check.md` 의 운영 SQL 이다.
2. **상태** `adult_check` 는 계정과 확인 시각뿐이다. 줄이 있으면 확인한 것이다. **CI · 생일 · 이름 · 번호를 두지 않는다** — KISA 안내의 연계정보 저장 제약 문의 답이 안 왔고 수집 항목은 정책이다. 계정을 지우면 함께 지워진다.
3. **판정** `adult_check_passed` 한 곳이다. 꺼져 있으면 누구에게나 참, 켜져 있으면 줄이 있는 사람만 참이다. **스위치 줄이 없으면 켜진 것으로 본다**(실패 때 닫힘). 함수의 실패는 그 문의 실패라 지나가지 않는다.
4. **적는 문** `confirm_adult_check` 는 열쇠 전용이다. 업체의 결과를 검증한 서버와 운영 SQL 만 쓴다. 사용자는 스스로 못 적는다.
5. **막는 자리 — 양쪽을 다 본다.** 미확인인 사람은 인연을 못 쓰고 남에게도 안 보인다.
   - 문장으로 거절: 추천 · 지나친 인연 · 요청 · 되살리기 · 수락 · 말 보내기 · 참여 켜기 — 「성인 확인을 먼저 마쳐 주세요.」
   - 빈 답(정지된 계정과 같은 모양): 요청 목록 · 인연 · 그 범위 · 채팅방 · 메시지 · 요청 소식 · 상대 사진
   - 상대가 미확인이면 그 카드 · 요청 · 인연 · 방이 안 보이고, 그 방에 보내면 없는 방과 같은 답이다. 확인하면 그대로 돌아온다. 지우는 것은 없다.
6. **안 막는 것.** 사주 · 궁합 · 저장(#947 본문). 받은 요청 거절 · 보낸 요청 취소 · 차단 · 신고 · 참여 끄기 · 탈퇴 — 떠나고 지키는 길은 확인을 묻지 않는다. `ensure_discovery_participation` 은 입력 저장 뒤에도 불려 던지지 않고 `skipped` 다.
7. **앱.** 껍데기가 인연 · 요청 · 채팅 주소에서 `my_adult_check` 를 읽고, 요구되는데 미확인이면 `/me/matching/adult-check?next=온 주소` 로 갈아 끼운다. 끝나면 `next` 로 돌아간다(ADR 0128 · 0213 의 그 값). 꺼져 있으면 읽기만 하고 화면은 그대로다. 못 읽으면 안내를 안 세운다 — 막는 것은 DB 다.
8. **업체 자리.** `AdultCheckProvider.start()` 하나다(`mobile/src/matching/adult-check.ts`). 지금은 `null` 이고 안내 화면에 단추가 안 선다. 앱은 업체의 답을 믿지 않고 서버를 다시 읽는다.
9. **심사 · 시험 계정은 운영 SQL 로 표시한다**(#947 범위 나눔). 화면 우회를 만들지 않는다.

## 실패했을 때

| 자리 | 답 |
| --- | --- |
| 스위치 줄이 없다 | 닫힌다 — pgTAP 이 잰다 |
| 앱이 상태를 못 읽는다 | 안내가 안 선다. 문이 거절을 말한다 |
| 업체를 마쳤는데 서버가 미확인이라 한다 · 못 읽는다 | 지나가지 않고 실패 줄이 선다 |
| 취소 | 제자리이고 말이 없다 |

## 고르지 않은 것

- **첫 배포부터 켠다** — 운영자가 막았다. 지금 배포된 웹 · 앱에는 확인할 길이 없다.
- **가입의 문(ADR 0101)** — 운영자 답은 인연 시작 때다. 켜는 PR 이 ADR 0101 · G-20 · 약관 제8조 · 처리방침의 문장을 함께 고친다. 꺼진 동안 약관은 그대로다.
- **미성년 판정을 표에 남기기** — 줄이 없는 것과 같은 답이라 칸을 늘릴 까닭이 없다.
- **상대 미확인 때 보이게 두기** — 「확인 전 프로필 노출 거절」(#947 본문)에 어긋난다.

## 잠그지 않은 것

- 켜 놓고 지나는 동안의 요청 만료 · 풀이권 예약은 그대로 돈다(만료되면 돌아온다).
- 풀이 보관함의 인연 궁합은 `visible_matches` 를 따라 미확인에게 안 보인다. 켜는 날의 표에 올린다.
- 같은 사람의 두 계정(CI)은 이번에 못 막는다 — 업체 · 저장 제약의 답 뒤다.

## 추기 2026-11-03 — 웹의 안내와 공개 시점 줄 (#947)

- **웹.** 관문(`proxy.ts`)이 인연 · 요청 · 채팅 주소의 화면 요청(GET)에서만 `my_adult_check` 를 계정 · 일정과 나란히 읽고, 요구되는데 미확인이면 `/me/matching/adult-check?next=온 주소` 로 보낸다. 판정은 앱과 같은 `adultCheckDetours`(`src/lib/matching/adult-check.ts`)다. 서버 액션은 안 돌린다. 못 읽으면 안 보내고 문의 거절이 말한다. 안내 화면은 꺼져 있거나 확인했으면 `next` 로 돌아간다. 잠그는 것은 여전히 DB 다 — 이 갈래가 통째로 틀려도 열리는 문은 없다.
- **공개 시점 줄.** 운영자가 자동 참여를 유지했다(2026-11-02, #947 댓글). 미확인 계정은 남에게 안 보이므로 확인이 곧 공개 시점이다. 앱 · 웹 안내에 「확인을 마치면 다른 회원에게 내 프로필이 보여요. 설정에서 끌 수 있어요.」가 선다(대장 matching-16).
- **서버 문은 아직 안 세웠다.** 업체의 결과를 검증해 `confirm_adult_check` 를 부르는 문은 열쇠를 드는 새 자리라(`app/keyed-client.ts` 의 목록 · `eslint.config.mjs` `KEY_HOLDERS` · `scripts/layers.test.ts`) 업체가 정해져 요청 모양을 알 때 함께 세운다. 그때까지 앱의 `adultCheckProvider` 와 웹 안내 화면의 단추 자리는 비어 있다.
- **두 스위치의 겹침.** 대화 흐름(ADR 0215 · 0216)이 켜진 동안에도 무료 대화 요청 · 끝난 대화가 확인을 묻는 것을 pgTAP 이 잰다(`99_adult_check`).
