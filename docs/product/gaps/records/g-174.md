# G-174 기록

표의 줄: [간극 대장 「정비 — 위임 준비」의 G-174](../../gaps.md#정비--위임-준비)

2026-11-21 조율자가 Vercel 대시보드에서 Cron Jobs 의 「Legacy — Schedules 로 옮기라」를 보았다. 옮길지 잰 기록이다. 플랜은 Hobby,
크론은 일곱(`vercel.json` 의 `crons` — reading · audit-export · photo-sweep · chat-purge · store-voided · store-consume · store-prices), 모두 GET 이고
자격은 `app/api/cron/authorized.ts` 의 `Authorization: Bearer <CRON_SECRET>` 하나다.

## 공식 문서가 말하는 것 (2026-11-21 읽음)

- **멈추는 날 — 없다.** 「Cron Jobs are a legacy feature and will be migrated to Schedules in the future」
  (<https://vercel.com/docs/schedules/migrate-from-cron-jobs>, 2026-10-09 고침). 공개 베타 공지(<https://vercel.com/changelog/vercel-schedules-is-now-in-public-beta>,
  2026-11-05)는 「Existing Cron Jobs continue to work」라 하고 날을 적지 않는다.
- **Schedules 는 공개 베타다.** 「Schedules are in beta, and these limits may change before general availability」(<https://vercel.com/docs/schedules/limits>).
- **Hobby 에서 된다.** 한 배포가 정적 일정 100 개까지, 팀에 1,000 개. 지터 창은 늘 15분이라 가장 잦은 것이 15분마다다 — 일곱은 다 하루 한 번이다.
  **새 한도**: 달마다 실행 5,000 회 · 동적 일정 생성 500 회(손으로 돌린 Run 도 센다). 넘으면 다음 결제 기간까지 일정 실행을 **건너뛴다**(같은 쪽).
  일곱이 하루 한 번이면 달에 약 217 회다.
- **설정** — `vercel.json` 의 `crons` 배열을 `schedules` 객체(이름이 열쇠)로 바꾸고, 같은 `path` · `schedule` 에 `"requestMethod": "GET"` 을 단다(path 일정의 기본은
  POST). 둘을 함께 두면 한 번에 두 번 돈다. 시간대를 안 적으면 UTC 그대로다. Production 배포가 현재 배포가 될 때 일정이 서고 옛 Cron Jobs 가 멈춘다
  (<https://vercel.com/docs/schedules/migrate-from-cron-jobs>).
- **자격 · 머리** — path 일정은 `user-agent: vercel-cron/1.0` · `x-vercel-cron-schedule` · `Authorization: Bearer <CRON_SECRET>` 를 그대로 싣고 `ce-*` 머리를
  더한다. 싣는 `CRON_SECRET` 은 현재 배포가 지어질 때의 값이다. 값에 머리에 못 드는 글자(끝 줄바꿈 등)가 있으면 그 빌드가 `INVALID_CRON_SECRET` 로 실패한다
  (<https://vercel.com/docs/schedules/handle-runs>).
- **시각** — Hobby 의 Cron Jobs 는 「정한 시(時) 안의 아무 때」, Schedules 는 「정한 분부터 15분 창 안」이다. Schedules 쪽이 좁다.
- **그 밖의 차이**(<https://vercel.com/docs/schedules/concepts>) — 늦게 배달할 수 있고(창 + 간격이 지나면 건너뜀), 같은 실행이 두 번 올 수 있으며, 재시도는 없다.
  롤백하면 그 배포의 일정으로 돌아간다. 대시보드의 Disable Cron Jobs 는 Schedules 를 멈추지 않는다 — 일정마다 Disable 이다.

## 판단 — 지금은 옮기지 않는다 (2026-11-21)

라우트 코드 · 자격 · 응답의 뜻은 그대로 옮겨지고 시각은 오히려 좁아진다. 그래도 지금 옮기지 않는 까닭:

1. 멈추는 날이 없다 — 지금 일곱은 그대로 돈다.
2. Schedules 는 베타라 한도가 GA 전에 바뀔 수 있고, Hobby 에 **넘으면 건너뛰는 달 실행 한도**가 새로 든다 — 결정 점검표(`docs/agents/delegation/decisions.md`)의
   「비용 · 요금 · 외부 서비스 — 플랜 · 한도」 줄이다.
3. 이 저장소의 도구가 아직 옛 꼴을 부른다 — `scripts/aws-wizard.sh` 의 `vercel crons run`, 런북의 Cron Jobs **Run**. 이 맥의 Vercel CLI 54.0.0 에는
   `vercel schedules` 가 없다(2026-11-21 `vercel schedules --help` 가 deploy 도움말을 찍었다).

## 옮길 때의 걸음

1. `vercel.json` — `crons` 를 지우고 같은 일곱을 `schedules` 로. 이름은 경로 끝(`reading` · `audit-export` …), `schedule` 은 그대로, `requestMethod: "GET"`,
   `timezone` · `jitter` 는 적지 않는다.
2. `scripts/aws-wizard.sh` 의 `vercel crons run "$CRON_PATH"` 를 `vercel schedules invoke audit-export` 로(CLI 를 올린 뒤) — `scripts/aws-wizard.test.ts` 의 가짜도.
3. 런북의 Cron Jobs 자리(`jobs.md` · `credits.md` · `moderation.md` · `security.md` · `photo-store.md` · `deploy.md`) — 「Cron Jobs 탭 → Run」을 「Schedules → 그 일정 → Run Schedule」로,
   「Hobby 는 ±59분」을 「15분 창」으로.
4. 결정 점검표의 한도 줄이라 ADR 하나와 운영자 답을 머지 전에 받는다.
5. 배포 뒤(「배포」 답 뒤) — Schedules 화면에 일곱이 서고 Cron Jobs 탭이 비었나 · 일정마다 Run Schedule 이 200(키 전 store-* 는 `{"configured":false}`)인가 ·
   다음 날 `audit-export-watch` · `photo-sweep-watch` · `chat-purge-watch` · `store-consume-watch` 알림이 조용한가. 값은 #770 에.
