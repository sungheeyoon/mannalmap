## 목표와 권한 봉투

- 운영자가 준 차례: 웹 공개 출시 → D-U-N-S 번호 전에 Expo 앱 마무리 → 안드로이드 계정 · 앱 배포 → 결제.
- 출시 단계를 공개 출시로 옮긴 #1011 뒤로 `ask` 가 머지 · `db push` 까지 묻게 됐다. 운영자가 「배포 전에만 물어보면」이라 해 #1067 이 `ask` 를 프로덕션 배포 넷으로 좁혔다(ADR 0093 추기).
- **#1067 로 실호출(`READING_LIVE` 등)의 도구 잠금도 함께 빠졌다.** 운영자에게 알렸고, 에이전트가 실호출을 안 돌리는 것은 이제 규약 문장만 정한다(`docs/agents/delegation/permissions.md` 「권한 등급」).
- 운영 배포 둘은 각각 「배포」 답 뒤였다 — 둘 다 DB 를 먼저 올렸다. 값은 #770.

## 운영자 결정

- 앱 푸시는 FCM 을 직접 쓴다(ADR 0236). 무료 · 예외 풀이권은 기한이 없다(ADR 0235) — 공지 받을 이용자가 운영자뿐이라 공지 없이 배포일 시행, 머지 직전 계정 수를 다시 확인했다(6, #770).
- 앱의 약관 메뉴는 웹의 현행 버전을 연다(#1066, ADR 0172 추기). 최소 버전을 못 읽으면 막지 않는다(fail-open). 업데이트 화면의 작은 링크는 「웹에서 계정 관리」(#1065, ADR 0237).
- 앱의 로그인 전 궁합(G-137)은 출시 뒤에 정한다 — 대장에서 `보류`.
- 빌드 실패를 덮어쓰기로 막지 말고 최신 공식 문서 · 한국 서비스 사례 · 앱이 그 값에서 도는지를 먼저 보라(아래 「헤맨 것」 9).

## 판단과 까닭

- **#1063 을 닫았다.** 조율자가 「앱 약관에 웹으로 가는 링크 한 줄」을 해결책째 브리프로 줬고, 에이전트는 법적 글이 빌드에 묶인 구조를 보지 않고 증상만 고쳤다.
  구조를 이슈(#1064)로 다시 적고 약관 셋을 웹으로(#1066), 재확인 기준과 최소 빌드를 서버로(#1065) 옮겼다.
- **카카오 모듈의 `compileSdk` 33 은 Gradle 덮어쓰기 대신 3.2.0 으로 풀었다(#1072).** 라이브러리 저장소의 고친 커밋과 npm tarball 의 그 줄을 보고 올렸다.
  문서 도메인 rnkakao.dev 는 다른 도메인(도박 사이트)으로 301 — 남의 손으로 넘어간 듯하다. 3.2.0 은 CI 출처 증명 없이 관리자가 손으로 올린 버전이라 조율자가 앞 버전과 tarball 을 견줬다 — 설치 스크립트 없음, 새 바깥 주소는 kakao 것뿐.
  문서는 저장소 원본 mdx 를 본다(`docs/ops/runbook/kakao-login.md`).
- doctor 버전 맞춤(#1073)으로 zod 높음 취약점이 감사에서 사라져 앱 감사 예외를 지웠다(ADR 0104 추기의 조건).
- EAS `preview` 빌드 셋 — `ebef4d0c` 실패(카카오 Maven 저장소, → #1071) · `4b3d8c51` 실패(`compileSdk` 33, → #1072) · `63d07224` 성공(`f112e2f6`). 버전과 빌드의 지금 값은 `docs/ops/runbook/mobile-release.md` 「버전 — Android SDK 와 의존」 · 「빌드와 제출」.
