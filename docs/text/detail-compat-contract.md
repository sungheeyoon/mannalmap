# 상세 궁합 출력 계약

> **정한 것은 §9 다 — 운영자 위임으로 조율자가 정했다(2026-11-02).** 상수 · 함수 · 시험은 `src/lib/reading/detail.ts` 에 섰고 부르는 곳은 §10 이다 — 인연 궁합은 상세 궁합 하나다(2026-11-04). 정책 원본은 PRD 매칭 §6.6 이다.
> §2 ~ §8 의 잰 값 기준은 main `3a6e47a`, 2026-11-02 이고 §5 의 갈래는 그때의 재료다. 실호출을 하지 않았다 — 글 품질 · 점수 분포 · 재호출 흔들림은 **못 쟀다**(「운영자 실호출로 잴 것」).

표시는 넷이다. **[코드 사실]** 코드에서 잰 것 · **[운영자 결정]** 운영자 직접 발언 · **[추천]** 승인 아닌 제안 · **[미정]** 갈래와 대가만 적고 정하지 않은 것.
코드와 어긋나면 코드가 맞다. 답이 나면 그 줄의 표시를 바꾼다.

## 1. 이미 정해진 것

- **[운영자 결정]** 무료 점수는 예상임을 강조하고, 상세를 봤을 때 다른 느낌이어야 한다 — 「예측? 예상 된이런걸좀 강조해야하고 상세를봣을때다른느낌을」(#961 표 A).
- 그 밖의 표기 · 소제목 · 비유 → 발견 → 점수 순서 · 카드 78점은 #961 표 C 의 추천이다. 이 문서도 그렇게 다룬다.

인연 궁합은 `kind: 'match'` 다. 화면 이름은 「궁합풀이」다.

- **낱말:** 프롬프트에 「끌리는 이유」 · 「연락과 속도」 · 「발견」 칸이 없다. 「연락의 속도」는 옛 판 절 안의 낱말이고 운영이 안 쓴다(`prompt.ts:1294`). 지금 판의 「연락 방식 · 결정 속도 · 갈등 반응」은 분류명을 풀어 쓰는 예시다(`prompt.ts:657`).
- **`private` 의 예외:** `my_reading` 은 `private` 원문을 안 자른다(마이그레이션 `:264`). 웹은 서버 경계에서 자르지만, 앱의 `mobile/src/compat/data.ts:226` 은 이 문을 직접 불러 응답에 근거 절이 든다. 화면에는 안 그린다. 그래서 「사용자에게 안 나간다」는 화면에서 참이고, 본인 `private` 의 응답 수준에서는 아니다.

## 3. 「더 많은 요소를 살핀다」는 참인가 — **[코드 사실]** 조건부

**카드와 기준점은 같은 자이고**(`previewScoreOf` `src/lib/discovery/index.ts:214`, 부르는 곳 `src/lib/reading/index.ts:119`), 인연은 언제나 연인용이며(`discovery/index.ts:199`) 읽는 값은 셋이다(`discovery/index.ts:177-182`, 무게 `:82`).

| 입력 | 카드 · 기준점 | 상세의 조정 입력 |
| --- | --- | --- |
| 두 일주끼리의 관계 | 40% — 일간 · 일지만 본다(`src/lib/discovery/compat-axes.ts:150-155`) | **다시 안 센다**(`prompt.ts:1170`) |
| 필요한 기운 보완 | 40% — 억부 1순위와 가장 무거운 오행 | **자료에 없다.** 제한형은 억부를 뺀다 |
| 합친 오행 균형 | 20% — 네 기둥의 글자 수 | 다시 안 센다 |
| 년 · 월 · 시가 하나 이상 걸린 사이 관계 | 없음 | 있음 |
| 함께 이룬 삼합 · 방합 · 삼형 | 없음 | 있음 |
| 서로를 보는 십성 · 걸린 자리의 무게(재량) | 없음 | 있음 |

- **참인 쪽:** 상세의 모델은 카드 셈이 안 읽는 값을 받는다. 임의의 생일 두 벌 5,000쌍을 엔진으로만 재 보니(1975~2005, 날은 1~28일, 시드 고정, **실제 이용자 분포 아님**) 조정 근거 관계가 있는 쌍은 시각을 알 때 5,000 · 모를 때 4,997, 중앙값 16줄 · 8줄이다. 함께 이룬 구조가 있는 쌍은 3,307 · 1,933 이다.
- **거짓인 쪽:** 상세가 카드의 전부를 포함하지 않는다. 필요한 기운 값은 모델이 못 본다. 카드도 네 기둥의 글자 수를 세므로 「카드는 일주만 본다」도 틀린다.
- **못 잰 쪽:** 받은 값을 모델이 실제로 썼는지는 코드로 알 수 없다 — 근거 줄이 검사 밖 평문이다. 그래서 「더 많은 자료를 넘긴다」는 사실이고, 「더 많이 보고 점수를 냈다」는 글마다 보증되지 않는다.
- 같은 표본의 연인용 기준점은 p5 37 · p50 56 · p95 74(시각 모름 33 · 55 · 73)다. ADR 0060 의 「50~77」은 옛 판 `discovery-v1` 의 수다. 78점은 이 표본의 p95 위이고, 카드의 맨 위 판정 칸(75 이상, `discovery/index.ts:319`)이다(D6 의 재료).
- 조정 근거가 없는 쌍이 이 표본에서 시각을 모를 때 3쌍뿐이라, 규칙 3의 「아무것도 안 걸렸으면 내리는 쪽 근거」는 거의 안 닿는 갈래다.

### 점수 변화 이유의 모양 — [미정]

| 갈래 | 얻는 것 | 대가 |

| 한 문장(글자 칸 하나) | 짧고 화면에 맞는다. 작은 수의 항목을 약속하지 않는다 | 수가 맞는지 기계로 못 잰다 |

**[추천]** 한 문장. 옛 판의 재호출 흔들림 ±3(ADR 0052)을 지금 판으로 다시 재기 전에 작은 수를 내보이지 않는 편이 안전하다. 실호출 결과가 나오면 다시 본다.

### 칸을 더한다면 지킬 것 — [추천]

- **평문 근거를 파싱하지 않는다.** 근거 줄 · `markdown` 소제목 · `>` 줄에서 값을 뽑아 화면이나 저장 칸을 채우지 않는다. 이 항목은 #963 범위이고 ADR 0208 도 화면이 절 구조를 모르게 했다.
- 궁합 전용 스키마를 세우고, 칸은 `markdown` 뒤에 둔다(지금 `markdown → score → metaphor`, ADR 0207 추기). 개인 풀이 스키마는 안 바꾼다.
- 새 칸이 실패해도 글을 버리지 않는다 — 비유처럼 적고 빈 값으로 저장한다(`metaphorToStore`, `collect.ts:273`). 이미 만든 글과 옛 앱에는 칸이 비고, 비면 화면이 그 자리를 안 세운다(PRD §1.5 의 비유 선례).
- 새 칸은 상대에게도 간다. 본문이 받는 검사(동의 밖 판정 이름 · 경로 샘 · 출생 입력 샘)를 **같이** 받는다 — 지금 검사는 본문 기준이라 저절로 안 걸린다.
- 점수 수를 본문에 적지 말라는 규칙(`prompt.ts:1187-1188`)을 유지한다.
- **D7 · 소제목은 프롬프트 본문을 바꾼다.** `pairVersion` 을 올리고 실호출 한 번이 든다(`docs/agents/test-map/what-to-run.md`).

## 5. 갈래 — [미정]

### D7 「적어도 한 항목은 움직인다」

| 갈래 | 얻는 것 | 대가 |
| --- | --- | --- |
| 지운다(#961 추천) | 움직일 까닭이 없을 때 지어 움직이지 않는다 | 예상과 같은 점수가 나올 수 있다. 「상세에서 달라진다」(표 B)는 말을 못 하고, 다른 느낌은 글이 져야 한다. 같아질 때의 화면이 필요하다 |
| 그대로 둔다 | 숫자가 거의 늘 달라진다는 기대에 맞다(보증은 아니다, 검사 없음) | 움직인 까닭이 억지일 수 있고, 그 까닭을 보이면 더 드러난다 |
| 그대로 두고, 점수가 기준점과 같으면 검사가 품질로 적는다 | 규칙이 지켜지는지 처음으로 잰다. 글은 안 막는다 | 검사 코드가 하나 늘고, 억지로 움직이는 문제는 그대로다 |

어느 갈래든 분포는 운영자가 다시 잰다(§7).

바꾸는 곳: `prompt.ts:1171-1172` · 주석 `:1138-1143` · `parts.test.ts:351-356` · `pairVersion` · PRD §1.4 · ADR 0060 추기. 규칙 머리의 「규칙 여섯」 번호도 함께.

### `private` 궁합에 함께 적용하나

조정 규칙은 한 상수 `SCORE_SECTION` 을 두 kind 가 쓰고(`prompt.ts:1530`), 판본도 하나다.

| 갈래 | 얻는 것 | 대가 |
| --- | --- | --- |
| 함께 | 지시가 한 벌이다 | `private` 는 카드를 안 거쳐 「예상 → 상세」 맥락이 없다 — 그 쪽은 「궁합 베타」 지표뿐이다(D10). 안 바뀌어도 될 글의 분포가 바뀐다. 실호출이 kind 마다 든다 |
| 인연 궁합만 | 범위가 좁다 | 점수 절이 kind 로 갈린다. 판본이 하나라 `private` 새 글의 판 이름이 안 바뀐 채 오른다 — `policy.ts:73-75` 가 피한 일이다. 판을 가르면 칸이 하나 늘어난다 |

## 6. 화면이 약속해도 되는 말 · 안 되는 말

아래는 **문장의 내용**이지 화면 문구가 아니다. 글자는 #964 · #965 가 대장 규칙으로 넣는다.

| 내용 | 지금 코드로 | 조건 |
| --- | --- | --- |
| 카드 점수는 몇 가지 기준으로 낸 예상이다 | 된다 | — |
| 상세는 두 사람의 자리 관계 등을 자료로 넣어 글을 쓴다 | 된다 | §3 |
| 상세 점수는 예상과 다를 수 있다 · 오를 수도 내릴 수도 있다 | 된다 | D7 과 무관 |
| 왜 달라졌는지 말해 준다 | **안 된다** | 칸이 서고 실호출로 본 뒤 |
| 반드시 달라진다 | **안 된다** | 검사가 없다. 지우면 더욱 |
| 더 정확하다 · 진짜 궁합 | **안 된다** | 정확도를 잰 적이 없다. 지금 고지는 「예측하거나 판정하지 않는다」(`app/match-index.tsx:121`) |

**[코드 사실]** 카드의 「예측」은 지금 눈에 안 보인다 — 웹 · 앱 다 화면 읽기 글자뿐이고(`app/me/matching/today-card.tsx:179`, `mobile/src/matching/today.tsx:75`), 보이는 것은 수와 「아주 좋은 궁합일 수 있어요.」 꼴의 판정이다. 운영자의 「예상 강조」는 #964 · #965 의 일이다.

## 7. 운영자 실호출로 잴 것 — 에이전트가 안 돌린다

구현 PR 뒤, 프롬프트 판마다. 명령 · 결과 파일 · 판정 기준은 `docs/ops/runbook/match-talk.md` 「상세 궁합 실호출」이다 — `READING_LIVE` 는 상세 모양을 안 부른다. `private` 도 함께면 그 kind 까지(`READING_LIVE`).

1. 점수와 기준점의 차 분포 — 0 이 얼마인가(D7 전후), 위아래 치우침, ±25 를 넘은 수.
2. 같은 짝 재호출의 흔들림 — 옛 판 ±3 이 지금도 맞는가. 변화 이유가 재호출마다 뒤집히는가.
3. 점수 근거 줄이 실제로 쓰이는가 · 합이 맞는가, 조정 입력을 실제로 드는가(§3 의 「못 잰 쪽」).
4. 변화 이유 · 발견 한 줄을 두면: 분류명 · 작은 수가 새는가, 점수와 본문이 같은 말을 하는가.
5. 다루는 내용 넷을 글마다 다루는가, 인연 궁합이 오래 만난 사이처럼 안 쓰이는가, 글이 서로 비슷해지지 않는가.
6. 칸을 더한 스키마로 비용 · 길이 · 실패율(`collect` 의 실패 기록)이 달라지는가.
7. **막힘 발생률** — `pillar-named-in-reading` 으로 막힌 글의 몫과, 막힌 글이 정말 기둥을 쓴 것인지(오탐). 높으면 검사를 풀기 전에 프롬프트부터 고친다.

## 8. DB 칸이 필요한가

| 경우 | DB | 넘길 곳 |
| --- | --- | --- |
| D7 · 소제목 · 다루는 내용만 | **필요 없음** | #963 에서 프롬프트 · 시험만, #962 와 병렬 |
| 변화 폭만 화면에 | **필요 없음** — `score_baseline` 이 있다. 옛 글은 비어 있다 | 화면 |

## 9. 정한 것 — 조율자, 운영자 위임(2026-11-02)

**인연 궁합은 상세 궁합 하나다**(대화가 유일한 흐름, 2026-11-04) — 옛 흐름(수락과 함께 나는 인연 궁합)의 지시와 스위치는 걷었고, 인연 궁합의 4판은 늘 아래 지시를 받는다. `private` · 개인 풀이의 글자와 판본은 그대로이고, `scripts/old-reading-prompts-unchanged.test.ts` 가 글자의 지문으로 잰다(원복용 옛 컷 조립은 2026-11-08 에 지웠다 — ADR 0239) — 인연 궁합의 지문은 걷기 전 상세 조립의 글과 같다.

1. **D7** — 상세에서 「적어도 한 항목은 움직인다」를 지운다. 까닭이 없으면 기준점 그대로가 맞다. 화면 약속은 「달라질 수 있어요」까지다.
2. **다루는 내용** — 고정 소제목을 두지 않는다(ADR 0067 · 2026-09-15 구성을 안 되돌린다). 글이 **연락 · 속도 · 표현 차이 · 부딪힐 때 맞춰 볼 점**을 빠뜨리지 않게 지시하고 소제목은 글이 짓는다. 어겼는지 기계가 모른다 — 사람이 대조한다. ADR 0139 와의 관계는 그 추기.
3. **발견 한 줄** — 스키마 칸 `discovery`(차례 `markdown` → `score` → `discovery` → `metaphor`)로 받아 저장 때 `reading.output` 맨 앞 문단으로 접는다(`withDiscovery`). **새 DB 칸이 없다.** 첫 문단이 리드로 서서 웹 · 앱을 안 고치고, 본문 검사 · 호칭 바꾸기를 함께 받는다. 평문을 되파싱하지 않고, 화면이 그 줄만 따로 꺼낼 수는 없다. §8 의 「필요함」은 따로 칸을 세울 때의 말이다.
4. **점수 변화 이유** — 내보내지 않는다. 칸이 없고 프롬프트가 쓰지 말라고 한다.
5. **`private` · D10** — 안 건드린다. 인연 궁합의 판본은 `detailVersion`(`reading-prompt-detail-v1`, `promptVersionOf('match')`)으로 따로 세고 `pairVersion` 은 비공개 궁합의 v23 그대로다.
6. **낱말** — 화면의 「상세 궁합」 · 「예상 궁합」은 운영자 방향이다. 약관의 「궁합풀이」 · 「예측」 정리는 #938 몫이다.
7. **글 안 직접 노출** — §6.6 의 15 를 따른다. 상세 글(본문 · 발견 한 줄 · 비유)이 두 사람의 **실제 기둥 두 글자**를 직접 쓰면 **막는다**(`pillar-named-in-reading`, 조율자 2026-11-02, ADR 0163 추기). 글은 두 사람이 함께 읽으므로 어느 자리든 누군가에게는 상대의 글자다. 한자는 그대로 찾고, 한글 읽기는 기둥을 부르는 말 곁이나 그 사람의 호칭 바로 뒤에서만 찾는다 — 「기사」 · 「임신」 같은 일상어를 안 걸려고 좁혔다. 막힌 글은 있는 실패 길로 가 풀이권이 복원되고, 비용은 실패 때 모델 호출 1회다. 근거 절은 재지 않는다 — 인연 궁합은 DB 문이 자른다(§2). 한 글자 · 관계 이름 · 오행으로 돌려 쓴 것은 잡지 않는다. **글에서 상대 글자를 유추할 위험이 있고, 직접 언급 금지만 검증했으며, 복원 불가를 보장하지 않는다.** 복원을 막는 검사는 두지 않는다(운영자 2026-11-02).

**문구.** 이 PR 이 넣는 화면 문구는 없어 대장 줄도 없다 — 발견 한 줄은 모델이 쓴다. 소제목 사례는 §5 대로 찾지 못했고, 발견 한 줄에 해당하는 한국 서비스 사례는 이번에 찾지 않았다.
