# 운영 절차 — 인연을 여닫기 (ADR 0222)

색인은 `docs/ops/runbook.md` 다.

## 인연의 스위치

**지금은 닫혀 있고 열지 않는다**(운영자 결정 2026-11-04 — 사주부터 운영한다). 카드 · 대화 · 채팅 · 상세 궁합이 한 스위치 뒤에 있다.
바꾸면 배포 없이 다음 요청부터 듣는다. 웹 · 앱의 탭 · 입구는 화면을 다시 열 때 따라온다.

지금 값 읽기(개인을 가리키지 않는다):

```sql
select open, changed_at from public.match_open_switch;
select public.match_is_open();
```

## 여는 조건

셋이 다 갖춰지기 전에는 열지 않는다. 하나라도 없으면 멈춘다.

1. **카카오의 답** — 운영정책 제4조(만남주선) 예외 검토와 카카오 로그인의 관계(G-131 · G-135). **섰다(2026-11-05, ADR 0222 추기)** — 인연에 성인 인증 기능을 적용하면 되고,
   카카오인증서 말고도 본인확인 · 간편인증 기관의 연령인증을 쓸 수 있다. 2 의 성인 확인을 같은 날 켜면 이 답의 요구도 선다. 원문은 `docs/legal/adult-check-grounds.md` 「카카오 운영정책 — 데브톡의 답」
2. **본인확인** — 성인 확인(#947, ADR 0214)의 업체 · 서버 문이 서서 `docs/ops/runbook/adult-check.md` 「켜는 차례」를 **같은 날** 밟을 수 있다.
   참여는 닫힌 동안에도 자동으로 켜져 있으므로, 성인 확인이 켜져야 확인이 곧 공개 시점이 된다
3. **수요 측정** — 사주 사용자 수와 인연 참여 의사. 기준은 운영자가 정한다. 참여 의사는 홈의 「열리면 알려 주세요」 신청 수다(ADR 0223) — 수만 센다(개인을 가리키지 않는다):

   ```sql
   select count(*) as asked from public.match_open_alert;
   ```

## 여는 차례

1. **승인** — 운영자에게 표로 묻는다: 여는 시각 · 위 셋의 근거 · 성인 확인을 함께 켜는가 · 참여 중인 계정 수(집계) · 알림 신청 수(위 3)
2. **성인 확인을 먼저 켠다** — `adult-check.md` 의 7. 인연이 닫혀 있는 동안이라 아무에게도 안 보인다
3. **연다**

   ```sql
   update public.match_open_switch set open = true, changed_at = now() returning open, changed_at;
   ```

4. **신청한 사람에게 알린다** — 신청한 활성 계정마다 서비스 안의 소식 한 줄(「인연이 열렸어요」 꼴)을 넣고 `match_open_alert` 를 비운다. 푸시 · 이메일은 쓰지 않는다(ADR 0223).
   그 소식 종류 · 화면은 아직 없다 — 여는 날 앞에 그것을 더하는 PR 이 먼저다(G-135)
5. **잰다** — 실기기와 웹에서 탭 넷 · 카드 · 대화 · 채팅. 깔린 앱(새 빌드 전)은 `match_talk_open()` 이 참이 되어 대화를 그린다. 끝나면 #770 에 줄을 더한다

## 닫기 · 되돌리기

```sql
insert into public.match_open_switch (id, open) values (true, false)
on conflict (id) do update set open = false, changed_at = now()
returning open, changed_at;
```

지우는 것은 없다 — 다시 열면 인연 · 방 · 말이 그대로 돌아온다(90일 보존은 그대로 돈다). 스위치 줄을 지우지 않는다 — 줄이 없으면 닫힌 것이다.

## 배포 차례 (이 판을 처음 올릴 때)

닫힘 마이그레이션은 `20270106120000` 이고, **운영에 안 오른 인연 파일 가운데 맨 앞에 선다** — 운영의 마지막 판 `20270106090000` 바로 뒤,
`20270107090000` · `20270107100000` · `20270108154600` · `20270109090000` 앞이다. CLI 의 `db push` 는 파일마다 트랜잭션을 묶어 커밋하므로:

- 첫 파일(닫힘)이 커밋되는 순간 운영의 옛 흐름(카드 · 풀이권을 맡기는 요청 · 수락 · 채팅)이 닫힌다
- 뒤 파일이 다시 쓰는 요청 · 답 · 상세 문(`20270107090000` · `20270109090000`)도 같은 판정을 부른다 — 어느 경계에서 멈춰도 닫혀 있다
- 어느 파일이 실패하면 그 파일만 되돌아가고 앞 경계(닫힘)가 남는다. 닫힘 파일 자신이 실패하면 운영은 지금과 같은 옛 판(열림)에 남는다 — 그때는 멈추고 고친다

경계마다의 확인은 로컬에서 `node scripts/match-closed-boundaries.mjs` 가 한다(올리기 전에 한 번, 끝나면 `npm run db:reset`).

1. 승인 — 운영자. 올리기 전에 운영의 마지막 판이 `20270106090000` 인지 본다(`npx supabase migration list` — 개인정보 없음). 다르면 멈춘다 — 닫힘 파일이 맨 앞이 아니게 된다
2. 운영 `db push` — 다섯 파일이 차례로 오른다. 첫 파일부터 운영의 인연이 닫힌다. 웹 · 깔린 앱의 인연 탭은 거절 문장(「인연은 준비 중이에요.」)과 빈 목록을 보인다
3. 웹 배포 — 탭 · 입구가 걷히고 주소가 홈으로 간다
4. 앱 새 빌드 · 스토어 심사 — 탭 · 입구가 걷힌다. 그 전의 깔린 앱은 탭이 남지만 문이 모두 거절한다. 앱에는 OTA 가 없다 — `mobile/` 에 `expo-updates` · `runtimeVersion` 이 없어(#932 「OTA 없음」) 앱이 바뀌는 길은 새 빌드 · 스토어 심사뿐이다. OTA 를 쓰려면 첫 스토어 빌드에 `expo-updates` 가 들어 있어야 하고, 둘지는 조율자가 따로 정한다.

확인(개인 없음):

```sql
select public.match_is_open() as open_now, public.match_talk_open() as legacy_answer;
```
